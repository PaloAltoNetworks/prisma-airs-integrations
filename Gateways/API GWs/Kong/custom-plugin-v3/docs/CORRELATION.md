# `transaction_id`, `session_id`, and why `tr_id` is wrong

This is the one change in the set that contradicts a written repo convention, so
it needs its own note rather than a code comment.

## What the convention says

This repository's own contribution guidance — `CLAUDE.md` and `CONTRIBUTING.md`
at the root, in the integration checklist and the payload example — instructs
integrations to send `tr_id`. The existing Kong integrations follow it:
`custom-plugin`, `custom-plugin-v2` and `request-callout` all populate `tr_id`,
in both their handlers and their documented payloads.

## What the API actually does

Measured against the live sync scan API, 8 requests, varying one field at a time:

| Sent | Transaction slot in SCM | Session slot in SCM |
|---|---|---|
| `transaction_id` only | filled | server-minted `pan_…` |
| `tr_id` only | server-minted `pan_…` | **filled with the tr_id value** |
| `session_id` only | server-minted `pan_…` | filled |
| `session_id` + `tr_id` | server-minted `pan_…` | filled from **`session_id`** |
| `transaction_id` + `session_id` | filled | filled |

Two conclusions, both reproducible:

1. **The transaction slot is filled only by `transaction_id`.** `tr_id` never
   reaches it.
2. **`tr_id` is a legacy alias for the session slot**, and it loses to
   `session_id` when both are present. Precedence is
   `session_id` › `tr_id` › server-minted.

Correlation ids are capped at 100 characters; longer values are rejected with a
non-200, which the plugin turns into a fail-closed 503.

## Why it matters

Kong was sending a **per-request** value as `tr_id`. So:

- The transaction slot was server-minted on every scan — the one id that should
  have tied a verdict back to a specific gateway request was generated by AIRS
  and never seen by Kong.
- The session slot received a value that changed every turn, which made **every
  message its own singleton conversation**. Nothing in SCM could group a
  multi-turn exchange, which is precisely the view you need to investigate a
  gradual jailbreak.

One field, wrong on both counts.

## What the plugin sends now

```json
{
  "transaction_id": "<Kong's own request id, from kong.request.get_id()>",
  "session_id": "<stable per conversation, or OMITTED>",
  ...
}
```

No `tr_id` at all.

`session_id` resolves in this order: `Mcp-Session-Id` (MCP defines it, and it is
also adopted from the *response* when the server issues it on `initialize`) →
`config.session_id_header` → `config.session_id_claim` from the bearer token →
the authenticated consumer.

**If none of those identify the conversation, `session_id` is omitted rather
than invented.** A per-request value in that slot is the original bug; sending
one deliberately would be worse than sending nothing, because it looks correct.

## What upstream needs changing

The three convention lines above should read `transaction_id` (per request) and
`session_id` (per conversation), with a note that `tr_id` is a deprecated alias
for the session slot and should not be used in new integrations. Every
integration in the repo is currently following the convention faithfully and
therefore has the same defect.
